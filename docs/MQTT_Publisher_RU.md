# MQTT Publisher — Подробное справочное руководство

**Многопоточный публикатор MQTT-метрик для встраиваемых Linux-систем**

Многопоточный публикатор метрик, читающий данные из INI-конфигурационного файла и публикующий их на MQTT-брокер с заданными интервалами. Предназначен для автоматизации, домашней автоматизации и мониторинга на устройствах с ограниченными ресурсами, таких как Raspberry Pi.

## Обзор

MQTT Publisher — лёгкая программа на C, предназначенная для сбора системных метрик из различных источников и их публикации на MQTT-брокер. Программа создана для сценариев автоматизации — от домашней автоматизации на Raspberry Pi до промышленного мониторинга на встраиваемых Linux-платах.

Программа читает один INI-конфигурационный файл, описывающий подключение к MQTT-брокеру и список метрик. Каждая метрика указывает, откуда читать данные (файл, shell-команда или удалённый MQTT-брокер), как часто публиковать и в какой MQTT-топик.

### Принципы проектирования

- **Минимум зависимостей** — только libmosquitto и pthreads, доступные практически в любом дистрибутиве Linux.
- **Низкие накладные расходы** — каждая метрика работает в собственном потоке с настраиваемым интервалом; без демона опроса, без среды выполнения скриптов.
- **Совместимость с procfs** — файловые источники используют `open()`+`read()` вместо `fopen()`+`fread()` для избежания проблем буферизации stdio на псевдофайловых системах.
- **Отказоустойчивость** — если брокер недоступен при запуске, программа молча повторяет попытки. Если удалённый брокер падает, локальные метрики продолжают работу.
- **Управление через конфигурацию** — нет жёстко заданных метрик, нет встроенных порогов. Всё в одном INI-файле.

### Типичные сценарии

| Сценарий | Как |
|----------|-----|
| Домашняя автоматизация | Публикация температуры, влажности и нагрузки CPU в Home Assistant через MQTT |
| Мониторинг Raspberry Pi | Передача температуры CPU/GPU, памяти, диска на центральный брокер |
| Сбор данных с датчиков | Чтение DHT11/DHT22 через [DHT-драйвер](https://github.com/chapvic/dht-driver) (procfs) и ретрансляция через MQTT |
| Агрегация с нескольких устройств | Приём метрик с удалённых MQTT-брокеров и их концентрация на центральном |
| Промышленный мониторинг | Чтение данных ПЛК через shell-скрипты и публикация на MQTT-брокер SCADA |

## Возможности

- **Многопоточная публикация** — каждая метрика в отдельном потоке с независимым интервалом.
- **Три типа источников** — файлы, shell-команды (префикс `@`) и удалённые MQTT-брокеры (префикс `$`).
- **Извлечение значения** — извлечение конкретного значения из многострочного вывода по литеральному ключу (`key=T`) или через POSIX ERE-регулярные выражения (`key=/pattern/`).
- **Мост к удалённому брокеру** — подписка на топик удалённого брокера и ретрансляция полученных значений на локальный.
- **Гибридный режим** — удалённые метрики поддерживают событийную публикацию (без `interval`) или публикацию по таймеру (с `interval`).
- **Разделяемые подключения** — подключения к удалённым брокерам дедуплицируются по `host:port`, несколько метрик с одного брокера используют одно соединение.
- **Авто-реконнект** — автоматическое переподключение к локальному и удалённым брокерам с ограниченной задержкой (1–60 секунд).
- **Неблокирующая настройка удалённых брокеров** — недоступный удалённый брокер не влияет на локальные метрики.
- **INI-конфигурация** — все настройки в одном файле; метрики не задаются через командную строку.
- **Аутентификация** — поддержка username/password для локального и удалённых брокеров.
- **QoS для каждой метрики** — QoS 0, 1 или 2 для каждой метрики.
- **Плавная остановка** — корректное завершение по SIGINT/SIGTERM с join всех потоков и очисткой ресурсов.
- **Режим отладки** — подробный лог каждой публикации, события подключения и ошибки.
- **Валидация конфигурации** — полная проверка с информативными сообщениями об ошибках при запуске.
- **Интеграция с systemd** — Makefile с целями `install`/`uninstall`, systemd-юнит и файл окружения.

## Требования и сборка

### Зависимости

- **GCC** (или совместимый компилятор C)
- **libmosquitto** — клиентская библиотека Mosquitto (`libmosquitto-dev` в Debian/Ubuntu, `mosquitto-devel` в Fedora/RHEL)
- **pthread** — POSIX-потоки (часть glibc во всех Linux-системах)

### Ручная сборка

```bash
gcc -O2 -Wall -Wextra -Werror -o mqtt_pub mqtt_pub.c -pthread -lmosquitto
```

| Флаг | Назначение |
|------|-----------|
| `-O2` | Оптимизация второго уровня |
| `-Wall -Wextra` | Все основные предупреждения компилятора |
| `-Werror` | Предупреждения трактуются как ошибки |
| `-pthread` | Линковка библиотеки POSIX-потоков |
| `-lmosquitto` | Линковка клиентской библиотеки Mosquitto |

Результат — исполняемый файл `mqtt_pub` в текущей директории.

## Установка

### Цели Makefile

В проекте есть Makefile со следующими целями:

| Цель | Описание |
|------|----------|
| `make` или `make all` | Скомпилировать `mqtt_pub` |
| `make install` | Установить бинарник, systemd-юнит, конфиг и env-файл; запустить сервис |
| `make uninstall` | Остановить сервис, удалить все установленные файлы (сохраняет `install.log`) |
| `make clean` | Удалить скомпилированный бинарник |
| `make distclean` | Удалить бинарник и `install.log` |

### Параметры установки

Параметры передаются в командной строке `make install`:

| Параметр | По умолчанию | Описание |
|----------|-------------|----------|
| `HOST` | `127.0.0.1` | Адрес MQTT-брокера (hostname или IP) |
| `PORT` | `1883` | Порт MQTT-брокера |
| `MQTT_USER` | _(пусто)_ | Имя пользователя для аутентификации |
| `MQTT_PASS` | _(пусто)_ | Пароль для аутентификации |
| `CONF` | `/etc` | Директория для конфигурационного файла |

### Примеры установки

```bash
# Установка по умолчанию (localhost:1883, без аутентификации, конфиг в /etc)
make install

# Свой брокер и аутентификация
make install HOST=192.168.1.100 PORT=1883 MQTT_USER=monitor MQTT_PASS=secret

# Своя директория для конфига
make install CONF=/etc/mqtt_pub

# Полная настройка
make install HOST=broker.local PORT=8883 MQTT_USER=admin MQTT_PASS=pass123 CONF=/etc/mqtt_pub
```

### Обработка конфигурационного файла при установке

Цель `make install` следует следующему приоритету:

1. **Если `mqtt_pub.ini` существует в папке проекта** — он копируется в назначение, а параметры из командной строки (`HOST`, `PORT`, `MQTT_USER`, `MQTT_PASS`) применяются поверх через `sed`. Преднастроенные пользователем метрики сохраняются.
2. **Нет локального конфига и нет в назначении** — создаётся минимальный конфиг с переданными (или стандартными) параметрами.
3. **Нет локального конфига, но есть в назначении** — обновляются только параметры-override; существующие метрики сохраняются.

### Что устанавливается

| Файл | Назначение | Описание |
|------|-----------|----------|
| `mqtt_pub` | `/usr/local/bin/mqtt_pub` | Исполняемый файл |
| `mqtt_pub.service` | `/etc/systemd/system/mqtt_pub.service` | systemd-юнит |
| `mqtt_pub.ini` | `$CONF/mqtt_pub.ini` | Конфигурационный файл |
| env-файл | `/etc/default/mqtt_pub` | Файл окружения с `PARAMS=-f <путь_к_конфигу>` |
| `install.log` | папка проекта | Записывает путь `CONF` для корректного удаления |

### Управление сервисом systemd

```bash
# Запуск
systemctl start mqtt_pub

# Остановка
systemctl stop mqtt_pub

# Перезапуск
systemctl restart mqtt_pub

# Статус
systemctl status mqtt_pub

# Автозапуск
systemctl enable mqtt_pub

# Отключить автозапуск
systemctl disable mqtt_pub

# Логи
journalctl -u mqtt_pub -f
```

### Удаление

```bash
make uninstall
```

Останавливает и отключает сервис, удаляет бинарник, systemd-юнит, env-файл и конфиг. `install.log` сохраняется в папке проекта.

## Использование

### Синтаксис командной строки

```
mqtt_pub [-f <config_file>] [-h]
```

| Параметр | Описание |
|----------|----------|
| `-f <config_file>` | Полный путь к INI-конфигурационному файлу. По умолчанию — `mqtt_pub.ini` в текущей директории. |
| `-h` | Вывод справки и завершение работы. |

### Примеры

```bash
# Запуск с конфигом по умолчанию (mqtt_pub.ini в текущей директории)
./mqtt_pub

# Запуск с указанным конфигом
./mqtt_pub -f /etc/mqtt_pub/my_metrics.ini

# Вывод справки
./mqtt_pub -h
```

### Запуск как сервис systemd

После `make install` сервис управляется через systemd. Файл окружения `/etc/default/mqtt_pub` содержит:

```
PARAMS=-f /etc/mqtt_pub.ini
```

Чтобы изменить путь к конфигу, отредактируйте env-файл и перезапустите сервис:

```bash
echo 'PARAMS=-f /etc/mqtt_pub/production.ini' | sudo tee /etc/default/mqtt_pub
sudo systemctl restart mqtt_pub
```

## Конфигурационный файл

Конфигурация задаётся в INI-формате. Файл состоит из необязательной секции `[MQTT]` (настройки подключения к брокеру) и одной или нескольких секций метрик.

### Формат файла

- Строки, начинающиеся с `#` или `;` — комментарии, игнорируются.
- Пустые строки игнорируются.
- Каждая секция начинается с заголовка `[section_name]`.
- Параметры задаются в виде `key=value`.
- Пробелы в начале и конце ключа и значения обрезаются.

### Секция [MQTT]

Секция настроек подключения к MQTT-брокеру. Если отсутствует, используются значения по умолчанию: хост `localhost`, порт `1883`, без аутентификации.

**Секция `[MQTT]` должна быть первой в конфигурационном файле, если присутствует.**

| Параметр | Описание | По умолчанию | Лимит |
|----------|----------|-------------|-------|
| `host` | Адрес MQTT-брокера (hostname или IP) | `localhost` | 256 байт |
| `port` | Порт MQTT-брокера | `1883` | 1–65535 |
| `user` | Имя пользователя для аутентификации | — | 64 байта |
| `password` | Пароль для аутентификации | — | 256 байт |
| `debug` | Режим отладки: `0` — тихий, `1` — подробный | `0` | — |

**Аутентификация:** Флаг включается при указании `user` или `password` (или обоих). Если указан только `password` без `user`, в качестве имени пользователя передаётся пустая строка — брокер сам решает, принимать ли подключение.

### Секции метрик

Каждая метрика описывается отдельной секцией с уникальным именем. Имя секции используется в диагностических сообщениях и выводе при запуске.

| Параметр | Описание | Обязательный | По умолчанию | Лимит |
|----------|----------|-------------|-------------|-------|
| `topic` | MQTT-топик для публикации значения | Да | — | 512 байт |
| `interval` | Интервал публикации в секундах | Да (нет для `$`-источника без interval) | — | > 0 |
| `source` | Источник данных: файл, `@shell_command` или `$remote` | Да | — | 2048 байт |
| `qos` | Уровень QoS: `0`, `1` или `2` | Нет | `0` | 0–2 |
| `key` | Ключ для извлечения значения (литерал, regex или `-`) | Нет | _(пусто)_ | 64 байта |

**Уникальность:** Имена секций метрик и MQTT-топики должны быть уникальными в пределах файла. Дубликаты вызывают ошибку запуска.

### Параметр: source

Параметр `source` определяет, откуда программа читает значение метрики. Поддерживаются три режима, различающиеся по первому символу:

| Префикс | Режим | Пример |
|---------|-------|--------|
| _(нет)_ | Путь к файлу — открывается через `open()`, читается одним `read()` | `source=/sys/class/thermal/thermal_zone0/temp` |
| `@` | Shell-команда — выполняется через `popen()`, stdout используется как значение | `source=@vcgencmd measure_temp \| awk -F= '{print $2}'` |
| `$` | Удалённый MQTT-брокер — подписка на топик и ретрансляция | `source=$192.168.1.50:1883/sensors/temp` |

См. [Типы источников данных](#типы-источников-данных) для подробной документации.

### Параметр: key

Параметр `key` управляет обработкой сырого содержимого источника перед публикацией. Три режима:

| Значение | Режим | Описание |
|----------|-------|----------|
| _(пусто или отсутствует)_ | Полный payload | Всё содержимое источника обрезается от пробелов и публикуется как есть |
| `key_name` | Литеральный ключ | Построчный поиск `key_name=<value>`, публикация `<value>` |
| `/pattern/` | Regex | Применяется POSIX Extended Regular Expression; если есть группа захвата, возвращается первое захваченное значение; иначе — полное совпадение |
| `-` | Явное отключение | То же, что пустое — публикация полного payload без извлечения |

См. [Извлечение значения (key)](#извлечение-значения-key) для подробной документации.

### Параметр: interval

Параметр `interval` задаёт частоту публикации метрики в секундах.

- Для файловых и shell-источников: `interval` **обязателен** и должен быть больше 0.
- Для `$`-источников (удалённые брокеры): `interval` **необязателен**:
  - **Без `interval`**: событийный режим — значения публикуются немедленно при получении от удалённого брокера.
  - **С `interval`**: режим таймера — последнее полученное значение перепубликуется с указанным интервалом, даже если новых данных не поступало.

Sleep реализован инкрементально: 100 циклов по 100 мс, что позволяет потоку реагировать на сигнал остановки в течение ~100 мс.

### Параметр: qos

Уровень качества обслуживания MQTT для метрики:

| Значение | Название | Поведение | Накладные расходы | Сценарий |
|----------|----------|----------|-------------------|----------|
| `0` | At most once | Без подтверждения, fire-and-forget | Минимальные | Некритичные метрики, потеря допустима |
| `1` | At least once | Гарантированная доставка, возможны дубли | Средние | Важные метрики, потеря недопустима |
| `2` | Exactly once | Гарантированная доставка без дублей | Максимальные | Критичные метрики, дубли недопустимы |

См. [Уровни QoS](#уровни-qos) для подробностей.

### Параметр: topic

MQTT-топик для публикации значения метрики. Должен быть уникальным в пределах конфигурационного файла.

Рекомендации по именованию топиков:
- Используйте прямые слэши `/` для иерархии: `sensors/rpi/cpu_temp`
- Начинайте с категории: `sensors/`, `system/`, `home/`
- Включайте идентификатор устройства для мультиустройных систем: `sensors/rpi4-living/cpu_temp`
- Короткие, но описательные имена

## Типы источников данных

### Файловые источники

Если `source` не начинается с `@` или `$`, значение трактуется как путь к файлу. Программа открывает файл через `open()`, читает содержимое одним вызовом `read()` (до 8191 байт) и использует результат как значение метрики.

```ini
# Температура CPU из sysfs (Raspberry Pi)
source=/sys/class/thermal/thermal_zone0/temp

# Информация о памяти из procfs
source=/proc/meminfo

# Значение DHT-датчика из procfs
source=/proc/sensors/dht/gpio4/value
```

#### Совместимость с procfs и sysfs

Файловые источники используют `open()` + `read()` вместо `fopen()` + `fread()`. Это критично для procfs и sysfs:

- **procfs** (`/proc/...`): Псевдофайлы, генерируемые ядром на лету. `fread()` может блокировать или возвращать частичные данные из-за буферизации stdio. Один вызов `read()` возвращает полное содержимое.
- **sysfs** (`/sys/...`): Аналогично procfs — содержимое генерируется ядром. Подход `open()`+`read()` обеспечивает надёжное чтение.
- **Обычные файлы**: Работают с обоими подходами одинаково.

Размер буфера для чтения файлов — `MAX_RAW` (8192 байт). При превышении читаются только первые 8191 байт.

#### Обработка ошибок

- Файл не существует или недоступен — ошибка в лог, публикация пропускается.
- `read()` возвращает ошибку (не пустой вывод) — ошибка в лог, публикация пропускается.
- Завершающие пробелы и переводы строк всегда обрезаются.

### Источники — shell-команды

Если `source` начинается с `@`, оставшаяся часть выполняется как shell-команда через `popen()`. Программа читает stdout команды и использует его как значение метрики.

```ini
# Температура CPU через vcgencmd (Raspberry Pi)
source=@vcgencmd measure_temp | awk -F= '{print $2}'

# Свободная память в МБ
source=@free -m | awk '/^Mem:/ {print $4}'

# Load average за 1 минуту
source=@uptime | awk '{print $10}' | tr -d ','
```

#### Как работает popen()

`popen()` вызывает `/bin/sh -c "<команда>"`, поэтому доступен полный синтаксис shell: конвейеры, перенаправления, подстановка команд, переменные и т.д.

Stdout команды читается через `fread()` до `MAX_RAW` (8192) байт. Вызов `pclose()` проверяет код завершения:
- **Код 0**: данные публикуются нормально.
- **Ненулевой код**: в режиме отладки выводится `[warn]`, но данные **не отбрасываются** — команда могла вывести полезный результат до сбоя.

#### Обработка ошибок

- `popen()` не удался — ошибка в лог, публикация пропускается.
- `fread()` вернул ошибку I/O (не пустой вывод) — ошибка в лог, публикация пропускается.
- Ненулевой код завершения — предупреждение в отладке, данные сохраняются.
- Завершающие пробелы и переводы строк всегда обрезаются.

### Удалённые брокеры

Если `source` начинается с `$`, программа подписывается на топик удалённого MQTT-брокера и ретранслирует полученные сообщения на локальный брокер.

#### Синтаксис

```
$[user:pass@]host:port/topic
```

| Компонент | Обязательный | Описание |
|----------|-------------|----------|
| `user:pass@` | Нет | Учётные данные для удалённого брокера |
| `host` | Да | Hostname или IP удалённого брокера (буквы, цифры, `.`, `-`) |
| `port` | Нет | Порт удалённого брокера (по умолчанию 1883) |
| `topic` | Да | Топик для подписки (всё после первого `/`) |

#### Примеры

```ini
# Данные с удалённого датчика без аутентификации
source=$192.168.1.50:1883/sensors/temperature

# С аутентификацией
source=$user:pass@remote.broker.com:1883/floor1/humidity

# На порту по умолчанию (1883)
source=$broker.local/data/room_temp
```

См. [Мост к удалённому брокеру](#мост-к-удалённому-брокеру) для подробного описания архитектуры.

## Извлечение значения (key)

Параметр `key` обрабатывает сырой вывод источника перед публикацией. Особенно полезен, когда источник возвращает многострочные данные и нужно конкретное значение.

### Литеральный ключ

Когда `key` — обычная строка (не в `/.../` и не `-`), программа ищет построчно `key=<value>` и публикует `<value>`.

```ini
# /proc/sensors/dht/gpio4/value возвращает:
# H=45.2
# T=23.1
#
# Извлечь температуру:
key=T

# Извлечь влажность:
key=H
```

Поиск построчный: программа ищет строку, начинающуюся с ключа, за которым следует `=`. Значение — всё после `=` до конца строки. Пробелы в начале и конце обрезаются.

### Regex-ключ

Когда `key` заключён в `/.../`, содержимое между слэшами трактуется как POSIX Extended Regular Expression (ERE). Regex применяется к полному сыром содержимому с флагами `REG_EXTENDED | REG_NEWLINE`.

- **Если шаблон содержит группу захвата `()`**, возвращается первое захваченное значение.
- **Если группа захвата отсутствует**, возвращается полное совпадение.
- Результат обрезается от пробелов в начале и конце.

```ini
# Извлечь числовую температуру из "temp=52.3'C"
key=/^temp=([0-9]+\.?[0-9]*)/

# Извлечь влажность из "H=45.2"
key=/^H=([0-9]+\.?[0-9]*)/

# Найти строку с "temp=" и вернуть полное совпадение
key=/temp=[0-9]+\.?[0-9]*/

# Извлечь первое число с плавающей точкой из любой строки
key=/([0-9]+\.[0-9]+)/
```

#### Флаги regex

| Флаг | Значение |
|------|---------|
| `REG_EXTENDED` | Синтаксис POSIX ERE — поддерживает `+`, `?`, `|`, `{n,m}`, `()`, `[]` |
| `REG_NEWLINE` | `^` и `$` сопоставляются с началом/концом каждой строки, а не только всей строки; `.` не сопоставляется с переводом строки |

### Без извлечения (key=-)

`key=-` явно отключает извлечение. Всё содержимое источника обрезается и публикуется как есть. Эквивалентно отсутствию параметра `key`.

```ini
# Опубликовать полное содержимое файла
source=/proc/sensors/dht/gpio4/value
key=-
```

Используйте `key=-` для явного указания, что публикуется полный payload — для читаемости конфига.

### Справочник по regex

Программа использует POSIX Extended Regular Expressions (ERE). Краткий справочник:

#### Метасимволы

| Символ | Значение |
|--------|---------|
| `.` | Любой символ, кроме перевода строки |
| `*` | Ноль или более повторов |
| `+` | Один или более повторов |
| `?` | Ноль или один повтор |
| `^` | Начало строки (с `REG_NEWLINE`) |
| `$` | Конец строки (с `REG_NEWLINE`) |
| `|` | Альтернатива (ИЛИ) |
| `[]` | Класс символов |
| `()` | Группа захвата |
| `{n}` | Ровно n повторов |
| `{n,m}` | От n до m повторов |
| `\` | Экранирование следующего символа |

#### Частые шаблоны

| Шаблон | Сопоставляет |
|---------|-------------|
| `[0-9]+` | Целое число |
| `[0-9]+\.?[0-9]*` | Десятичное число (`23.1`, `45`, `0.5`) |
| `-?[0-9]+\.?[0-9]*` | Число со знаком (`-5.3`, `23.1`) |
| `[0-9]+\.[0-9]+` | Строго десятичное (`23.1`, не `45`) |
| `[a-zA-Z]+` | Буквенная строка |
| `[a-zA-Z0-9]+` | Буквенно-цифровая строка |
| `^([0-9]+)` | Число в начале строки |

#### Практические примеры

```ini
# Температура CPU из sysfs (возвращает миллиградусы)
# "48312" -> публикуем "48312" (деление на 1000 в потребителе)
source=/sys/class/thermal/thermal_zone0/temp
key=-

# Температура из vcgencmd: "temp=52.3'C"
# Извлечь только число
source=@vcgencmd measure_temp
key=/temp=([0-9]+\.?[0-9]*)/

# Значение DHT: "H=45.2\nT=23.1\n"
# Извлечь температуру
source=/proc/sensors/dht/gpio4/value
key=T

# То же через regex
source=/proc/sensors/dht/gpio4/value
key=/^T=([0-9]+\.?[0-9]*)$/

# Свободная память из /proc/meminfo: "MemFree:        123456 kB"
# Извлечь число
source=/proc/meminfo
key=/^MemFree:\s+([0-9]+)/

# Load average из uptime: "...load average: 0.15, 0.20, 0.10"
# Извлечь значение за 1 минуту
source=@uptime
key=/load average:\s+([0-9]+\.[0-9]+)/
```

## Совместимость с procfs

### Отличия procfs

procfs (`/proc`) и sysfs (`/sys`) — псевдофайловые системы: их файлы не хранятся на диске, а генерируются ядром на лету. Это имеет важные последствия для способа чтения:

| Аспект | Обычный файл | procfs/sysfs |
|--------|-------------|--------------|
| Хранение | На диске | Генерируется при каждом чтении |
| `fread()` | Читает весь файл | Может вернуть частичные данные или заблокировать из-за буферизации stdio |
| `read()` | Читает доступные байты | Возвращает полное содержимое за один вызов |
| Размер файла | Известен заранее | Неизвестен (stat может вернуть 0) |

MQTT Publisher использует `open()` + `read()` для файловых источников именно для корректной работы с procfs и sysfs. Shell-команды (`@`-префикс) используют `popen()` + `fread()` — это нормально, так как shell сам управляет буферизацией.

### Интеграция с DHT-драйвером

[DHT-драйвер](https://github.com/chapvic/dht-driver) — модуль ядра Linux для чтения датчиков DHT11/DHT22/AM2302 на GPIO-пинах Raspberry Pi. Данные датчиков доступны через procfs.

#### Иерархия procfs

```
/proc/sensors/dht/
├── debug           (rw) — отладка: 0 = выкл, 1 = вкл
├── version         (r)  — версия драйвера
├── export          (w)  — записать номер BCM-пина для регистрации датчика
├── unexport        (w)  — записать номер BCM-пина для удаления датчика
├── auto_interval   (rw) — глобальный интервал автоопроса (2–60, -1 = выкл)
└── gpio<pin>/
    ├── pin           (r)  — номер BCM GPIO-пина
    ├── interval      (rw) — интервал автоопроса для датчика (2–60, -1 = выкл)
    ├── measure       (w)  — записать "1" для запуска измерения
    ├── status_code   (r)  — код ошибки (0 = успех)
    ├── status_text   (r)  — описание ошибки
    ├── value         (r)  — "H=<влажность>\nT=<температура>\n"
    ├── info          (r)  — тип датчика + время регистрации
    └── timestamp     (r)  — Unix-время последнего измерения
```

#### Формат файла value

Файл `value` выводит две строки:

```
H=45.2
T=23.1
```

- `H=` — влажность в процентах с одним знаком после запятой
- `T=` — температура в градусах Цельсия с одним знаком после запятой; отрицательные значения с префиксом `-`

Пример с отрицательной температурой:

```
H=52.0
T=-5.3
```

#### Настройка MQTT Publisher с DHT-датчиками

```ini
# DHT22 на GPIO4 — температура
[dht_temp]
topic=sensors/dht22/living_room/temperature
interval=10
source=/proc/sensors/dht/gpio4/value
key=T
qos=1

# DHT22 на GPIO4 — влажность
[dht_hum]
topic=sensors/dht22/living_room/humidity
interval=10
source=/proc/sensors/dht/gpio4/value
key=H
qos=1

# Тот же датчик через regex
[dht_temp_regex]
topic=sensors/dht22/living_room/temperature
interval=10
source=/proc/sensors/dht/gpio4/value
key=/^T=(-?[0-9]+\.?[0-9]*)$/
qos=1
```

#### Настройка DHT-драйвера

1. **Сборка и загрузка** (см. [репозиторий DHT-драйвера](https://github.com/chapvic/dht-driver)):

```bash
# Сборка
make
sudo insmod dht.ko

# Регистрация датчика на GPIO4
echo 4 | sudo tee /proc/sensors/dht/export

# Включение автоопроса каждые 10 секунд
echo 10 | sudo tee /proc/sensors/dht/auto_interval

# Проверка
cat /proc/sensors/dht/gpio4/value
# Вывод: H=45.2\nT=23.1
```

2. **Авто-регистрация при загрузке** — создайте `/etc/default/dht`:

```
# Конфигурация DHT-драйвера
AUTO_INTERVAL=10
SENSOR=4
SENSOR=17,5
```

3. **Настройте MQTT Publisher** — добавьте метрики DHT в `mqtt_pub.ini`, как показано выше.

## Оптимизация shell-команд

Shell-команды мощны, но могут быть накладными на устройствах с ограниченными ресурсами вроде Raspberry Pi. Каждый вызов `@`-источника порождает процесс shell, что имеет накладные расходы. Следуйте этим рекомендациям:

### Предпочитайте файловые источники

Если метрика доступна как файл в procfs или sysfs, используйте файловый источник вместо shell-команды. Чтение файла значительно быстрее — нет порождения процесса, нет интерпретации shell.

```ini
# ХОРОШО: файловый источник (быстро)
source=/sys/class/thermal/thermal_zone0/temp

# ИЗБЕГАТЬ: shell-команда для тех же данных (медленнее)
source=@cat /sys/class/thermal/thermal_zone0/temp
```

### Минимизируйте количество процессов

Каждый `popen()` запускает `/bin/sh -c "<команда>"`, что может породить дополнительные процессы для конвейеров. Команда `@free -m | awk '/^Mem:/ {print $4}'` создаёт три процесса: `sh`, `free` и `awk`.

```ini
# Меньше процессов: awk читает /proc/meminfo напрямую
source=@awk '/^MemFree:/ {print $2}' /proc/meminfo

# Ещё лучше: файл + key (вообще без процессов)
source=/proc/meminfo
key=/^MemFree:\s+([0-9]+)/
```

### Выбирайте подходящие интервалы

Не все метрики нужно читать каждую секунду. Подбирайте интервал под скорость изменения:

| Тип метрики | Рекомендуемый интервал |
|-------------|----------------------|
| Температура | 5–15 секунд |
| Влажность | 10–30 секунд |
| Использование памяти | 10–60 секунд |
| Использование диска | 60–300 секунд |
| Сетевые статистики | 5–30 секунд |
| Частоты | 10–60 секунд |
| DHT-датчики | 10–30 секунд (минимум 2с между чтениями) |

### Избегайте тяжёлых команд

Некоторые команды накладны на Raspberry Pi:

| Команда | Проблема | Альтернатива |
|---------|---------|--------------|
| `top -bn1` | Читает /proc несколько раз | Используйте `/proc/stat` или `/proc/loadavg` |
| `ps aux` | Перечисляет все процессы | Используйте конкретные файлы `/proc/<pid>/` |
| `find /` | Обходит всю файловую систему | Используйте известные пути |
| `du -sh /` | Сканирует всё дерево | Используйте `df` для статистики разделов |

### Используйте key= вместо конвейеров

Вместо shell-конвейеров для извлечения значения читайте файл и используйте `key=`:

```ini
# МЕДЛЕННЕЕ: порождает grep + awk
source=@grep MemFree /proc/meminfo | awk '{print $2}'

# БЫСТРЕЕ: чтение файла + key (без процессов)
source=/proc/meminfo
key=/^MemFree:\s+([0-9]+)/
```

### Замер накладных расходов

Проверьте время выполнения shell-команды:

```bash
time vcgencmd measure_temp
time free -m | awk '/^Mem:/ {print $4}'
time awk '/^MemFree:/ {print $2}' /proc/meminfo
```

На Raspberry Pi 4 простая shell-команда занимает 5–20 мс. С 20 метриками и интервалом 10 секунд общие накладные расходы — около 0.1–0.4 секунды на цикл, что незначительно, но стоит контролировать.

## Мост к удалённому брокеру

### Архитектура

Когда `source` начинается с `$`, программа создаёт отдельный экземпляр Mosquitto для каждого уникального удалённого брокера (дедупликация по `host:port`). Клиент подписывается на указанный топик и ретранслирует сообщения на локальный брокер.

```
Удалённый брокер A        Локальный брокер
  topic: sensors/temp       topic: sensors/rpi/remote_temp
       │                          │
       └── $remote_A:1883/sensors/temp
              │
         mqtt_pub (remote client)
              │
         mqtt_pub (local client)
              │
         local broker:1883
```

Несколько метрик с одного удалённого брокера разделяют одно подключение. Поддерживается до `MAX_REMOTES` (32) удалённых брокеров.

### Событийный режим и режим таймера

#### Событийный (без `interval`)

Когда `interval` не указан для `$`-источника, метрика публикуется немедленно при получении сообщения от удалённого брокера. Минимальная задержка.

```ini
[remote_temp]
topic=sensors/rpi/remote_temp
source=$192.168.1.50:1883/sensors/temp
qos=1
# Без interval = событийный режим
```

#### Режим таймера (с `interval`)

Когда `interval` указан для `$`-источника, поток-таймер перепубликует последнее известное значение с заданным интервалом. Если сообщений ещё не было, ничего не публикуется. После получения значение кэшируется и перепубликуется по расписанию.

```ini
[remote_temp_buffered]
topic=sensors/rpi/remote_temp
source=$192.168.1.50:1883/sensors/temp
interval=30
qos=1
# interval=30 = перепубликация последнего значения каждые 30 секунд
```

Режим таймера полезен, когда удалённый источник публикует редко или нерегулярно, а вам нужен регулярный "пульс" для системы мониторинга.

### Разделяемые подключения

Когда несколько метрик подписаны на один удалённый брокер (тот же `host:port`), они разделяют одно подключение Mosquitto. Программа дедуплицирует подключения, сравнивая пары `host:port`:

```ini
# Обе метрики используют один удалённый брокер (192.168.1.50:1883)
# Создаётся только одно подключение
[remote_temp]
source=$192.168.1.50:1883/sensors/temp

[remote_humidity]
source=$192.168.1.50:1883/sensors/humidity
```

При переподключении (после сбоя сети) программа автоматически переподписывается на все топики этого брокера.

### Авто-реконнект

Подключения к удалённым брокерам используют `mosquitto_reconnect_delay_set()`:
- Начальная задержка: 1 секунда
- Максимальная задержка: 60 секунд
- Без экспоненциального роста (линейный retry)

Отключенный удалённый брокер повторяется каждую секунду, до раза в 60 секунд. При восстановлении программа выводит `[remote] <host>:<port> back online` и переподписывается на все топики.

### Отказоустойчивость

Настройка удалённых брокеров **некритична**:
- Если удалённый брокер недоступен при запуске — программа выводит предупреждение и продолжает. Локальные метрики не страдают.
- Если удалённый брокер падает во время работы — локальные метрики продолжают публиковаться.
- При некорректной конфигурации удалённого брокера (неверный хост, нет топика) — метрика пропускается с сообщением об ошибке.

## Принцип работы

### Жизненный цикл

1. **Парсинг аргументов** — чтение ключей `-f` и `-h`, определение пути к конфигу.
2. **Загрузка конфигурации** — INI-файл парсится и валидируется. Настройки брокера и метрики заполняются в глобальные структуры.
3. **Установка обработчиков сигналов** — `SIGINT` и `SIGTERM` перехватываются для плавной остановки.
4. **Инициализация Mosquitto** — `mosquitto_lib_init()`, создание клиента, установка учётных данных.
5. **Регистрация коллбэков** — `on_connect` и `on_disconnect`.
6. **Подключение к брокеру** — `mosquitto_connect()` с циклом повторных попыток: если брокер недоступен, программа повторяет каждую секунду с однократным логированием ошибки. После успешного подключения CONNACK опрашивается каждые 100 мс (до 2 секунд).
7. **Запуск сетевого цикла** — `mosquitto_loop_start()` запускает фоновый поток для сетевых событий и авто-реконнекта.
8. **Потоки локальных метрик** — для каждой метрики файла/shell создаётся `metric_thread`.
9. **Настройка удалённых брокеров** — `setup_remote_brokers()` создаёт удалённые подключения (неблокирующе). Для удалённых метрик с `interval` также запускается `remote_timer_thread`.
10. **Главный цикл** — главный поток спит циклами по 1 секунде, проверяя `g_running`.
11. **Остановка** — `cleanup_all()`: join всех потоков, остановка циклов удалённых брокеров, отключение и уничтожение всех экземпляров Mosquitto, очистка библиотеки.

### Модель потоков

| Поток | Количество | Назначение |
|------|-----------|-----------|
| Главный | 1 | Инициализация, главный цикл, обработка сигналов |
| Mosquitto loop (локальный) | 1 | Сетевые события локального брокера |
| Mosquitto loop (удалённый) | 1 на удалённый брокер | Сетевые события каждого удалённого брокера |
| `metric_thread` | 1 на локальную метрику | Чтение источника и публикация с интервалом |
| `remote_timer_thread` | 1 на удалённую метрику с `interval` | Перепубликация последнего значения |

### Потокобезопасность

- **`g_mqtt_mutex`** (глобальный) — защищает вызовы `mosquitto_publish()`. Только один поток публикует на локальный брокер одновременно.
- **`value_mutex`** (на метрику) — защищает `last_value` и `has_last_value` для удалённых метрик, предотвращая гонки между `remote_on_message` и `remote_timer_thread`.
- **`g_running`** (sig_atomic_t) — безопасно для чтения из любого потока и записи из обработчика сигнала.
- **`g_mqtt_connected`** (sig_atomic_t) — проверяется локальными потоками метрик перед публикацией.

### Коллбэки подключения

#### Локальный брокер

- **`on_connect`** — устанавливает `g_mqtt_connected` в `1` (успех) или `-1` (отказ CONNACK). В отладке выводит `[mqtt] connected to broker`.
- **`on_disconnect`** — сбрасывает `g_mqtt_connected` в `0`. Выводит неожиданное отключение, только если ранее было подключение и программа ещё работает.

#### Удалённые брокеры

- **`remote_on_connect`** — устанавливает `connected = true`, переподписывается на все метрики этого брокера. Логирует первичное подключение и переподключения.
- **`remote_on_disconnect`** — устанавливает `connected = false`. Логирует отключение один раз (без спама при повторах).
- **`remote_on_message`** — сопоставляет входящие сообщения с метриками по топику, применяет извлечение ключа, сохраняет `last_value` и немедленно публикует на локальный брокер.

## Обработка сигналов

| Сигнал | Поведение |
|--------|----------|
| `SIGINT` (Ctrl+C) | Устанавливает `g_running = 0`, инициирует плавную остановку |
| `SIGTERM` | Устанавливает `g_running = 0`, инициирует плавную остановку |

### Порядок остановки

1. `g_running` сбрасывается в `0`.
2. Все потоки метрик завершают цикл в течение ~100 мс (инкрементальный sleep).
3. `cleanup_all()` выполняет упорядоченное завершение:
   - `pthread_join` всех локальных потоков метрик
   - `pthread_join` всех потоков-таймеров удалённых метрик
   - Уничтожение `value_mutex` для каждой метрики
   - `mosquitto_loop_stop(true)` для локального и всех удалённых брокеров
   - `mosquitto_disconnect` + `mosquitto_destroy` для всех экземпляров
   - `mosquitto_lib_cleanup()`
   - `pthread_mutex_destroy(&g_mqtt_mutex)`
4. Программа выводит `Done.` и завершается с кодом 0.

## Уровни QoS

| QoS | Название | Поведение | Накладные расходы | Сценарий |
|-----|----------|----------|-------------------|----------|
| `0` | At most once | Без подтверждения | Минимальные | Некритичные метрики, потеря допустима |
| `1` | At least once | Гарантия доставки, возможны дубли | Средние | Важные метрики, потеря недопустима |
| `2` | Exactly once | Гарантия без дублей | Максимальные | Критичные метрики, дубли недопустимы |

> **Примечание:** QoS 1 и 2 требуют поддержки брокера. При QoS 0 сообщение теряется, если брокер недоступен в момент публикации. Потоки метрик проверяют `g_mqtt_connected == 1` перед публикацией — сообщения просто пропускаются (не ставятся в очередь), когда брокер недоступен.

**Рекомендации:**
- QoS 0 для частых, некритичных метрик (load average, сетевые статистики).
- QoS 1 для данных датчиков, где потеря чтения нежелательна (температура, влажность).
- QoS 2 использовать редко — накладные расходы значительны на ограниченных устройствах.

## Режим отладки

Включается параметром `debug=1` в секции `[MQTT]`.

### Тихий режим (`debug=0`, по умолчанию)

При запуске:
- Заголовок программы (имя, версия, лицензия, автор)
- Список метрик: имя секции и топик
- `Broker`, `Auth`, `Debug`, `Metrics` — сводка

Во время работы:
- Ошибки чтения источников и публикации → stderr

### Режим отладки (`debug=1`)

Дополнительно:
- Для каждой метрики: `topic`, `interval`, `source`, `qos`, `key`
- Каждая успешная публикация: `[pub] <topic> = <value>`
- Ошибки публикации: `[err] publish to <topic> failed: <error>`
- Ошибки чтения источника: `[err] failed to read source for [<section>]`
- Ключ не найден: `[err] key '<key>' not found in '<source>'`
- Regex не найден: `[err] regex '<pattern>' not found in '<source>'`
- События подключения: `[mqtt] connected to broker` / `[mqtt] connect failed: <error>`
- События отключения: `[mqtt] disconnected from broker` / `[mqtt] unexpected disconnect: <error>`
- События удалённых брокеров: `[remote] <host>:<port> connected` / `[remote] <host>:<port> back online`
- Подписки: `[remote] subscribe <host> -> <topic> (rc=<code>)`
- Предупреждения shell-команд: `[warn] command exited with code <N> for source '<source>'`
- Сообщение `Running... (Ctrl+C to stop)`

## Устранение неполадок

### Программа завершается при запуске

| Симптом | Причина | Решение |
|---------|---------|---------|
| `Error: cannot open config file` | Файл не найден или нет прав | Проверьте путь `-f`, права доступа |
| `Error: [MQTT] must be the first section` | Секция метрики перед `[MQTT]` | Переместите `[MQTT]` в начало файла |
| `Error: duplicate section` | Две секции с одинаковым именем | Переименуйте одну |
| `Error: duplicate topic` | Две метрики с одним топиком | Задайте уникальные топики |
| `Error: too many metric sections` | Больше 128 метрик | Разделите на несколько экземпляров |
| `Error: metric [<name>] has no source` | Нет параметра `source=` | Добавьте `source=` в секцию |

### Данные не публикуются

| Симптом | Причина | Решение |
|---------|---------|---------|
| `[mqtt] connect failed` | Брокер не запущен или неверный адрес | Проверьте брокер: `mosquitto_sub -h <host> -t '#'` |
| `[err] failed to read source` | Файл не найден или команда не сработала | Проверьте источник вручную |
| `[err] key not found` | Ключ не найден в содержимом | Проверьте содержимое файла и ключ |
| `[err] regex not found` | Regex не сопоставляется | Проверьте: `echo "<data>" \| grep -E '<pattern>'` |
| `[warn] command exited with code` | Команда завершилась с ошибкой, но вывела данные | Проверьте синтаксис; данные могут быть корректны |

### Проблемы с удалённым брокером

| Симптом | Причина | Решение |
|---------|---------|---------|
| `[remote] failed to parse source` | Неверный синтаксис `$`-источника | Проверьте формат: `$[user:pass@]host:port/topic` |
| `[remote] <host>:<port> unavailable` | Удалённый брокер не запущен | Проверьте доступность |
| Нет данных от удалённого брокера | Несовпадение топика или нет данных | Подпишитесь на топик напрямую для проверки |
| `[remote] too many remote brokers` | Больше 32 удалённых брокеров | Уменьшите количество |

### Сервис не запускается

```bash
# Статус сервиса
systemctl status mqtt_pub

# Логи
journalctl -u mqtt_pub -e

# Проверка конфига
ls -la /etc/mqtt_pub.ini

# Проверка env-файла
cat /etc/default/mqtt_pub

# Ручной запуск для диагностики
mqtt_pub -f /etc/mqtt_pub.ini
```

## Рекомендации по использованию

### Конфигурация

- **Группируйте метрики** — используйте согласованную иерархию топиков: `sensors/<расположение>/<метрика>`.
- **Подходящие интервалы** — не опрашивайте чаще, чем источник обновляется. DHT-датчикам нужно минимум 2 секунды между чтениями.
- **QoS 1 для данных датчиков** — QoS 0 может терять сообщения; QoS 2 редко оправдан.
- **Включайте отладку при настройке** — `debug=1` при конфигурировании, `0` для production.
- **Комментируйте конфиг** — добавляйте комментарии `#` с описанием метрики.

### Производительность на Raspberry Pi

- **Предпочитайте файловые источники** — `open()+read()` быстрее `popen()`.
- **Минимизируйте конвейеры** — каждый `|` порождает процесс.
- **Избегайте `cat`** — используйте файловые источники: `source=/proc/meminfo` вместо `source=@cat /proc/meminfo`.
- **Разнесите интервалы** — не ставьте всем метрикам `interval=5`. Комбинируйте 5, 10, 15, 30 секунд.
- **Контролируйте процессы** — каждая shell-метрика добавляет 2+ процесса на цикл.

### Безопасность

- **Используйте аутентификацию** — всегда `user` и `password` для брокеров, доступных не только с localhost.
- **Права на конфиг** — `chmod 640 /etc/mqtt_pub.ini` (устанавливается Makefile).
- **TLS** — если брокер поддерживает, настройте в `mosquitto.conf` и укажите соответствующий порт.
- **Изоляция через VPN** — для удалённых брокеров используйте VPN или частные сети.

## Примеры интеграции

### Home Assistant

В Home Assistant добавьте конфигурацию MQTT-сенсоров:

```yaml
# configuration.yaml
sensor:
  - platform: mqtt
    name: "CPU Temperature"
    state_topic: "sensors/rpi/cpu_temp"
    unit_of_measurement: "°C"
    qos: 1

  - platform: mqtt
    name: "Living Room Humidity"
    state_topic: "sensors/dht/living/humidity"
    unit_of_measurement: "%"
    qos: 1

  - platform: mqtt
    name: "Free Memory"
    state_topic: "sensors/rpi/mem_free_mb"
    unit_of_measurement: "MB"
```

### Node-RED

В Node-RED создайте MQTT-in узел, подписанный на ваши топики метрик:

```
[MQTT In: sensors/rpi/cpu_temp] → [Function: форматирование] → [Dashboard: gauge]
```

### Мульти-Raspberry Pi

Используйте удалённые источники для агрегации метрик с нескольких Pi на центральном брокере:

```ini
# На центральном брокере, в mqtt_pub.ini:
[pi4_temp]
topic=sensors/pi4/cpu_temp
source=$pi4.local:1883/sensors/rpi/cpu_temp
qos=1

[pi3_temp]
topic=sensors/pi3/cpu_temp
source=$pi3.local:1883/sensors/rpi/cpu_temp
qos=1

# Событийный: публикация немедленно при получении
[pi4_dht_temp]
topic=sensors/pi4/dht/temperature
source=$pi4.local:1883/sensors/dht/living/temperature
qos=1
```

### Полный пример конфигурации

```ini
# MQTT Publisher Configuration
# (c) 2026, Chapvic

[MQTT]
host=localhost
port=1883
user=monitor
password=secret
debug=0

# ── Температура ──

[cpu_temp]
topic=sensors/rpi/cpu_temp
interval=5
source=@vcgencmd measure_temp
key=/temp=([0-9]+\.?[0-9]*)/
qos=1

# ── Память ──

[mem_free]
topic=sensors/rpi/mem_free_kb
interval=10
source=/proc/meminfo
key=/^MemFree:\s+([0-9]+)/
qos=0

[mem_available]
topic=sensors/rpi/mem_available_kb
interval=10
source=/proc/meminfo
key=/^MemAvailable:\s+([0-9]+)/
qos=0

# ── Загрузка CPU ──

[load_avg_1m]
topic=sensors/rpi/load_avg_1m
interval=15
source=/proc/loadavg
key=/^([0-9]+\.[0-9]+)/
qos=0

# ── Диск ──

[disk_root_used]
topic=sensors/rpi/disk_root_used_pct
interval=60
source=@df -h / | awk 'NR==2 {print $5}' | tr -d '%'
qos=0

# ── DHT22 на GPIO4 ──

[dht_temp_living]
topic=sensors/dht/living/temperature
interval=10
source=/proc/sensors/dht/gpio4/value
key=T
qos=1

[dht_humidity_living]
topic=sensors/dht/living/humidity
interval=10
source=/proc/sensors/dht/gpio4/value
key=H
qos=1

# ── Удалённый брокер (событийный режим) ──

[remote_pi3_temp]
topic=sensors/pi3/cpu_temp
source=$pi3.local:1883/sensors/rpi/cpu_temp
qos=1

# ── Удалённый брокер (режим таймера) ──

[remote_pi3_load]
topic=sensors/pi3/load_avg_1m
source=$pi3.local:1883/sensors/rpi/load_avg_1m
interval=30
qos=0
```
